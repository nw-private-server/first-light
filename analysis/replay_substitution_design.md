# Replay-Substitution Design (extending past seq 0x24)

Status: DRAFT for review — no production code yet.
Author: Claude Opus 4.7 (1M)
Date: 2026-05-05

## 1. Problem statement

`server/javelin/replay_store.py:118` exposes `replay_messages_after_v3(max_seq=0x24)`,
which already filters out every captured message containing `XX` placeholders
(`replay_store.py:121-127`). Because every interesting post-V3 message *does*
contain redactions, the live replay currently stops at seq 0x24 — exactly
where the first big StateBundle (`seq 0x25`, 46 KB, type 0x8) would start.

The new live test (2026-05-05) shows that ~10 s after seq 0x24 the client's
render thread crashes for lack of world-init data. The community state-machine
dump (`docs/community/community_state_machine_dump.txt:34-60`) confirms this
is the expected mandatory burst (phases 4 / 6 / 8 / 14, "WORLD DATA",
"ENTITY DEFS", "GAME DATA", etc.).

We need a way to **substitute live-session values** into the redacted spans
of the captured messages so that we can ship seq 0x25..0x6c (and beyond)
on the wire without using Mixed Nuts' real account/persona/character bytes.

## 2. Inventory of redacted-field types in seq >= 0x25 (R-direction only)

Generated by walking `ReplayStore` and grouping `redacted_spans` by length.
103 R-direction messages live at seq >= 0x25; 54 of them carry redactions
(7.23 % of bytes, 4912 individual spans). Span-length histogram:

|    18  |   50  | Length-prefixed ASCII strings of length 21 (the `0x15` byte precedes `[`). Visible context shows them sitting inside `[...]` next to `@ui_spirit_shrine` — a character display name truncated/escaped. Lengths 18/19/20 reflect 21/22/23-char display names. |

W-direction also has 512 / 558-byte spans in seq 0x0 / 0x6 / 0x6b (JWT and

listed only for completeness.

### 2.1 Per-seq highlights for the 0x25..0x6c burst

- `0x25` (46 423 B, 161 spans): mix of 8 / 16 / 18 / 19 / 20-byte spans.
  Contains the `Mixed Nuts` literal at offset 0x2e3b followed by an 8-byte
  hash and a 16-byte UUID — the persona display-name + persona UUID pair.
- `0x29` (99 819 B, 857 spans of len 61): persona-id strings spamming
  the SkinCollection asset graph. Each is `amzn1.developerPersonaId.<uuid>`.
- `0x2a..0x6c` (16 messages, 161 spans each): identical span-shape to 0x25;
  these are repeated StateBundle init units that share the same identity
  references.
- `0x73..0xae` (StateBundle summaries, mostly 1-2 spans each): mostly 16-byte
  UUID + occasional 36-byte dashed UUID.
- `0x28` (153 B, type 0x16a0, 1 span of 36): single dashed UUID after
  `ItemPool$` — an item-instance UUID we can't currently source.

|-----------------------------------|---------------------------------------------------------------------------------------------------|------------|

| 36-byte session UUID (text)       | Same as above, ASCII form (already 36 chars including dashes).                                    | HIGH       |
| 61-byte persona-id text           | `parse_v3_request(...).persona_id` (`v3_request.py:55,124`). Already 61 chars when present.       | HIGH       |
| 16-byte persona UUID (binary)     | Hex-decode the UUID portion of `persona_id` (chars 25..61) → 16 B.                                | HIGH       |
| 36-byte persona UUID (text)       | Last 36 chars of `persona_id`. Use only when length matches.                                      | HIGH       |
| 16-byte character UUID            | **UNKNOWN from V3 alone.** Mixed Nuts' capture suggests a single character per persona. Source candidates: (a) reuse persona UUID, (b) generate a deterministic UUID5 from persona-id, (c) read from `auth_mock.make_fake_login_ticket(character_id=...)` (`auth_mock.py:264`). For now: emit a fixed deterministic stub and document the risk. | LOW       |
| 36-byte character UUID text       | Same source as 16-byte character UUID, ASCII form.                                                | LOW        |
| 18 / 19 / 20-byte display-name    | Captured were 21 / 22 / 23-char `[character-display-name]`-style strings. We have no live source for the user's chosen name — `auth_mock` doesn't store one. The Lumberyard `AZ_CRC` is well documented; if the hashing scheme matches, we can recompute. **Risk:** if the client validates the hash, a wrong CRC fails server-side. **Mitigation:** zero them and observe; if the client rejects, switch to recomputed CRCs. | MEDIUM |
| 32-byte session token             | `make_session_token()` (`v3_response.py:112`). Already used in the V3 response; we reuse it for any post-V3 reference — but session tokens didn't appear in the seq>=0x25 redaction list, so this field is informational only. | HIGH |
| 12-byte Steam user-id text (W)    | `parse_v3_request(...).platform_user_id`. **W-only** — not emitted by replay. | HIGH (unused) |
| JWT region (512 B, W)             | `auth_mock.sign_jwt(persona_id, ...)`. **W-only** — not emitted by replay. | HIGH (unused) |

### 3.1 Plumbing the V3 request into the substitution context

Today `_handle_v3_data_record_inner` (`rep_responder.py:309`) parses the
inbound V3 request once for logging, then a second time for session-uuid
extraction (`rep_responder.py:362-363`). The parsed result is **not stored
on `self`**. We need to keep it. Proposed:

```python
# rep_responder.py, just after the existing strict parse at ~line 363:
self.last_v3_request = req            # the V3RegistrationRequest dataclass
self.substitution_ctx = SubstitutionContext.from_v3_and_session(
    req=req,
    session_token=token,               # already computed above
    auth_state=getattr(self, "auth_state", None),  # optional bridge later
)
```

`auth_state` is a nullable hook for a future bridge to `auth_mock` (so we
can pull `character_id` etc. from the live auth ticket once the responder
shares state with the HTTPS mock). For now it stays None and we substitute
deterministic stubs for character fields.

## 4. Proposed substitution API

New module: `server/javelin/replay_substitution.py`. **Not** a rewrite of
`ReplayStore`; it consumes `ReplayMessage` instances and produces fresh
`bytes`. The store stays the single source of truth for parsed redactions.

```python
# server/javelin/replay_substitution.py  (skeleton — DO NOT IMPLEMENT YET)
from __future__ import annotations
from dataclasses import dataclass, field
from typing import Optional
from server.javelin.replay_store import ReplayMessage
from server.javelin.v3_request import V3RegistrationRequest


@dataclass
class SubstitutionContext:
    """Holds the live-session values used to fill redacted spans.

    Built once per session (after V3 parse). Immutable thereafter.
    """

    # --- Identity (high-confidence) ---
    persona_id_text: str            # "amzn1.developerPersonaId.<uuid>" (len 61)
    persona_uuid_bytes: bytes       # 16 B
    persona_uuid_text: str          # 36 chars
    session_uuid_bytes: bytes       # 16 B
    session_uuid_text: str          # 36 chars
    session_token: bytes            # 32 B (the V3 response token)

    # --- Identity (low-confidence — currently stubbed) ---
    character_uuid_bytes: bytes     # 16 B  -- DEFAULT: deterministic from persona
    character_uuid_text: str        # 36 chars
    character_display_name: str     # default "NWPrivateTester01"

    # --- Optional warnings/diagnostics ---
    warnings: list[str] = field(default_factory=list)

    @classmethod
    def from_v3_and_session(
        cls,
        *,
        req: V3RegistrationRequest,
        session_token: bytes,
        auth_state: Optional[dict] = None,
    ) -> "SubstitutionContext":
        """Construct from a parsed V3 request + the response session token.

        `auth_state` is a forward-compatibility hook (None for now).
        Anything we can't source gets a deterministic stub plus a warning.
        """
        ...

    def apply(self, msg: ReplayMessage) -> bytes:
        """Walk msg.redacted_spans and return a substituted body.

        Strategy per span (length-keyed):
          16  -> session/persona/character UUID-binary, dispatched by
                 looking at the bytes IMMEDIATELY before the span:
                   length-prefix 0x10 + scoped marker byte? See section 4.1.
          36  -> dashed-UUID text. Same dispatch as 16.
          61  -> persona_id_text, ASCII-encoded.
          18 / 19 / 20 -> length-prefixed character display name padded
                          / truncated to fit the captured length.
           8  -> AzCore CRC of the adjacent name string, OR zeros (configurable).

        Spans that don't match a known shape get the captured zero-fill
        and append an entry to `self.warnings` so the caller can log them.
        """
        ...
```

### 4.1 How to disambiguate same-length spans

A 16-byte span could be a session UUID, a persona UUID, or a character UUID.
We need a heuristic. From the captured contexts:

- **Pre-byte `0x05`** (length prefix in V3-style typed streams) +
  **immediate-pre type-id `[01 06]` or `[01 07]`** => persona UUID.
  See seq 0x77 @0x176: `pre=...07 55 6e 75 73 75 61 6c 05` (here a name
  string ends with `0x05` length prefix → next 16 B is a UUID following the
  name).
- **Inside the 0x6c StateBundle near `Mixed Nuts`** => persona UUID.
- **In the 0x80 StateBundle** => probably character UUID.

The dispatch table can start coarse (one rule per seq, e.g. "in seq 0x29
all 61-byte spans are persona_id") and refine as the test loop reveals
mismatches. We log every mismatch + the surrounding 12 B for offline
review. Concretely:

```python
SPAN_RULES: dict[tuple[int, int], str] = {
    # (seq, span_length) -> field_name
    (0x29, 61): "persona_id_text",
    (0x6c, 16): "persona_uuid_bytes",
    (0x25, 16): "persona_uuid_bytes",
    # ...
}
```

Anything not in the table falls back to a length-only default
(e.g. len 16 → persona_uuid_bytes) with a warning.

## 5. Where it plugs into rep_responder

Two surgical edits, both inside `server/rep_responder.py`. **No** new
classes added to that file.

### 5.1 Build the context on V3 receipt

Insert ~5 lines after the existing strict-parse fallback at
`rep_responder.py:399` (just before `resp = V3RegistrationResponse(...)`):

```python
# Stash the substitution context once we've parsed the V3 request.
try:
    from server.javelin.replay_substitution import SubstitutionContext
    self.substitution_ctx = SubstitutionContext.from_v3_and_session(
        req=req, session_token=token,
    )
    self.log.info(
        f"   substitution_ctx armed: "
        f"persona={self.substitution_ctx.persona_id_text[:30]}... "
        f"warnings={len(self.substitution_ctx.warnings)}"
    )
except Exception as e:
    self.log.warning(f"   substitution_ctx build failed: {e!r}")
    self.substitution_ctx = None
```

### 5.2 Apply during replay send

Inside `_send_replay_message` (`rep_responder.py:537`), replace the body
source on the line that builds `envelope_body`:

```python
# Before:
envelope_body = vlq32 + msg.body

# After:
ctx = getattr(self, "substitution_ctx", None)
if msg.has_redaction:
    if ctx is None:
        self.log.error(
            f"replay seq=0x{msg.seq:x} has redaction but no "
            f"substitution_ctx; dropping"
        )
        return
    body_bytes = ctx.apply(msg)
else:
    body_bytes = msg.body
# Recompute size after substitution (length should match; assert).
assert len(body_bytes) == len(msg.body), \
    f"replay-substitute changed body length: {len(msg.body)} -> {len(body_bytes)}"
msg_size = len(body_bytes)
# (existing VLQ32 calc unchanged)
envelope_body = vlq32 + body_bytes
```

### 5.3 Drop the redaction filter from `replay_messages_after_v3`

Currently `replay_store.py:121-127` filters out redacted messages. The
caller is the only call site (`rep_responder.py:509`). Two options:

- **Option A (preferred):** keep the filter as the default but add
  `include_redacted: bool = False` and pass `True` from the responder
  once `substitution_ctx` exists. Backwards compatible.
- **Option B:** remove the filter entirely and let the caller decide.

Option A reads cleaner because it leaves the existing test (the
`__main__` self-check at the bottom of `replay_store.py`) intact.

## 6. Test loop

1. **Unit test** for `SubstitutionContext.apply()` — feed a synthetic
   `ReplayMessage` with one span per length category and assert the
   length-preservation invariant + a few hex-dump fixtures. Lives at
   `tests/test_replay_substitution.py`.
2. **Round-trip parser test** — for each seq in 0x25..0x6c, build a
   `SubstitutionContext` from a fixture V3 request, run `apply()`, and
   assert (a) length matches, (b) no remaining 16-byte run of
   `00 00 00 00 ...` where there used to be a span, (c) every persona-id
   region decodes back to a 61-char ASCII string.
3. **Live test** — extend `--replay-max-seq` to `0x6c`, run a full client
   session, look for: (a) the render-thread CTD timer never fires, (b)
   the client logs progress past `state=13`. Per
   `docs/community/community_state_machine_dump.txt:80`, the gate to watch
   for is `WaitingForPlayerSpawn`.
4. **Stretch** — extend to `0x80..0xae` (the StateBundle summary range),
   verify state advances to 53 (line 21 of `handoff-notes.md`).

## 7. Risks and unknowns

| Risk                                                                 | Severity | Mitigation |
|----------------------------------------------------------------------|----------|------------|
| 8-byte AzCore-hash spans validate against the adjacent string and we recompute the CRC wrong. | HIGH | First pass: keep them zeroed and observe. If the client rejects, port `AZ_CRC32` from Open 3D Engine source. |
| Character UUID has no live source today. We emit a deterministic stub. | HIGH | Plumb `auth_mock.character_id` into the responder via a shared session-state object. Out of scope for v1. |
| Display-name length mismatch — the captured payload uses lengths 21 / 22 / 23, our stub may differ. | MEDIUM | Pad/truncate the configured stub to the captured length. Length-preservation is enforced by the assertion in 5.2. |
| Same-length spans in different positions mean different fields. | MEDIUM | `SPAN_RULES` table keyed on (seq, length, optional pre-byte signature). Start coarse, refine from live mismatches. |
| Some seq>0x24 messages encode UDP-level state the client cross-checks against the V3 response's session_token (not the session_uuid). | LOW | Stash the response token in the context; if the test loop reveals a token cross-check, wire it in. |
| Captured timing may differ from what the client tolerates. The current 50 ms pacing (`rep_responder.py:172`) was tuned for the 0x2..0x24 burst. | LOW | Tune `--replay-interval-ms` once we're past 0x24. |
| Seq 0x29 is 99 KB — single record will exceed the no-VLQ32 ceiling at `_send_replay_message`'s `raise ValueError(...)` (`rep_responder.py:554`). | HIGH | Need to add 3+ byte VLQ32 encoding before extending past 0x28. Out of scope of *substitution* itself but blocks the full burst replay. |

## 8. Things this design intentionally does NOT do

- **Does not modify `ReplayStore`**. The redaction-span data is already
  perfect for the substitution layer to consume.
- **Does not implement V3-request mirror substitution** (the W-direction
  stuff in seq 0x0 / 0x6b). We never replay W messages.
- **Does not change the Carrier wrap or VLQ32 encoding**. The 99 KB seq
  0x29 record will hit the existing `raise ValueError(...)` and is a
  separate follow-up.
- **Does not store session state across processes**. `substitution_ctx`
  is per-`ResponderSession` instance, same lifetime as `replay_queue`.

## 9. Open questions for review

1. Should `character_uuid_bytes` default to (a) a deterministic UUID5
   derived from persona-id, or (b) a zero UUID, or (c) wired through
   from `auth_mock`? Proposal: **(a)** for v1, with a `--character-uuid`
   override CLI flag.
2. Are there post-V3 fields we DO want to fail loudly on instead of
   stubbing? E.g. should an unmatched 36-byte span raise instead of
   warn?
3. Should we extend `replay_messages_after_v3` to a broader name like
   `replay_messages_in_range(start, end)` now that the redaction filter
   is going away? Proposal: leave as-is; only drop the filter via the
   `include_redacted` kwarg (section 5.3 Option A).
